# ESP32-S3 跌倒检测原型方案

## 1. 目标定义

本方案面向 `ESP32-S3` 的低成本、非接触式人体跌倒检测原型验证，目标不是一步做到商用品质，而是先做出一个可重复验证的 `V1`。

建议把第一阶段目标限定为：

- 单房间
- 单人场景
- 检测区固定
- 输出 `跌倒疑似 / 非跌倒 / 空闲`
- 允许前期通过 `PC` 做训练和推理，`ESP32-S3` 先负责稳定采集和事件上报

这样做的原因很直接：`ESP32-S3` 可以提供 `Wi-Fi CSI` 采集能力，但“跌倒检测”本身不是官方现成能力，真正的难点在于数据质量、环境稳定性和分类逻辑，而不是单纯把 `CSI` 回调跑起来。

## 2. 可行性判断

### 2.1 能不能做

可以做原型验证。

`ESP32-S3` 支持 `Wi-Fi CSI (Channel State Information)`，这为基于无线信道扰动的人体活动感知提供了底层基础。学术界已经有大量基于 `Wi-Fi CSI` 的跌倒检测研究，因此从技术路线看是可行的。

### 2.2 能做到什么程度

- 做实验原型：可行
- 做固定场景下的演示系统：可行
- 做高可靠商用品质跌倒报警：仅靠单路 `ESP32-S3 Wi-Fi CSI` 风险较高

### 2.3 主要限制

- `ESP32-S3` 是 `2.4GHz Wi-Fi`，不是专用雷达，分辨率和鲁棒性有限
- 官方现成组件更偏向 `人体存在检测`、`运动检测`，不是成熟的“跌倒分类器”
- 家具移动、天线方向、部署高度、多人活动、空调风、门开关都可能影响结果
- 跌倒检测需要区分 `跌倒`、`坐下`、`躺下`、`弯腰`、`快速下蹲`，难度高于简单的人体存在检测

## 3. 推荐系统拓扑

### 3.1 推荐方案

建议采用如下结构：

- `ESP32-S3 #1 (S3-RX)`：主接收节点，负责 `CSI` 采集、缓存、上报
- `ESP32-S3 #2 (S3-TX)`：辅助发包节点，提供可控链路
- `2.4GHz Router/AP`：固定信道、固定带宽，用于稳定组网
- `PC`：数据接收、标注、训练、可视化、在线验证
- `Alarm`：蜂鸣器、LED、MQTT 或串口告警

### 3.2 为什么不建议一开始只用单板

最低成本方案当然可以是：

- `1 x ESP32-S3 + 现有路由器 + PC`

但这种方案的问题是：

- 发包行为不受你控制
- 链路稳定性更依赖路由器
- CSI 分布更容易受环境因素影响
- 后续复现实验时一致性较差

因此，原型阶段更建议使用 `2 个 ESP32-S3`，至少让一条无线链路更可控。

## 4. 硬件建议

### 4.1 建议 BOM

- `ESP32-S3` 开发板 x2
- `2.4GHz` 路由器 x1
- 外置天线 x2
- 蜂鸣器或 LED x1
- 一台 PC

### 4.2 板卡选择建议

优先选择：

- 带 `IPEX` 外置天线接口
- 带 `PSRAM`
- 供电稳定
- 天线区域布局相对规范的开发板

原因：

- 外置天线更容易调方向和部署位置
- `PSRAM` 对缓存 `CSI` 数据和滑窗处理更友好
- 供电不稳会给无线链路带来额外不确定性

### 4.3 部署建议

- `S3-TX` 和 `S3-RX` 放在房间两侧
- 让无线链路穿过主要活动区
- 安装高度先从 `0.8m` 到 `1.2m` 试起
- 节点间距先控制在 `3m` 到 `6m`
- 优先覆盖床边、沙发边、起身区等高风险区域
- 初期不要频繁移动设备

这里的高度和距离是工程经验值，不是官方硬指标，后续要结合现场效果调整。

## 5. 软件栈建议

建议使用：

- `ESP-IDF 5.4+`
- `espressif/esp-csi`
- `espressif/esp-radar`
- `espressif/esp_wifi_sensing`

说明：

- `esp-csi` 用于底层 `CSI` 采集能力和参考示例
- `esp-radar` 和 `esp_wifi_sensing` 更适合作为前级 `人体存在/活动门控`
- “跌倒检测”需要你自己再叠加特征工程和分类模型

## 6. 系统分层设计

建议把系统拆成 4 层，不要把全部逻辑堆在 `CSI` 回调里。

### 6.1 采集层

职责：

- 启用 `Wi-Fi CSI`
- 注册 `esp_wifi_set_csi_rx_cb()`
- 将 `CSI` 数据轻量入队
- 不在中断/回调路径里做重计算

### 6.2 运动门控层

职责：

- 使用 `esp-radar` 或 `esp_wifi_sensing` 判断当前是 `ACTIVE` 还是 `INACTIVE`
- 只在明显活动时触发后续特征提取与分类
- 对空闲场景做过滤，降低误报和算力消耗

### 6.3 跌倒候选识别层

职责：

- 对 `1s` 到 `2s` 滑窗做特征提取
- 输出 `fall_candidate` 概率或分数

### 6.4 事后确认层

职责：

- 观察事件后的持续静止状态
- 避免把正常 `坐下`、`躺下`、`蹲下` 误判成跌倒

推荐逻辑：

- `快速剧烈变化 + 低位姿持续 + 后续低活动`

## 7. 数据流设计

建议前期采用“板端采集，PC 端处理”的方式：

1. `S3-RX` 采集 `CSI`
2. 通过 `UART`、`UDP` 或 `USB CDC` 发送到 `PC`
3. `PC` 负责：
   - 数据存储
   - 可视化
   - 人工标注
   - 特征工程
   - 模型训练
   - 在线推理验证

待模型稳定后，再决定是否把部分推理下沉到 `ESP32-S3`。

推荐演进路径：

- 阶段 A：`S3` 只采集，`PC` 推理
- 阶段 B：`S3` 采集 + 候选事件检测，`PC` 最终判定
- 阶段 C：`S3` 本地运行轻量模型

对原型阶段而言，建议先做 `A`。

## 8. 特征工程建议

### 8.1 第一版不要急着做相位

第一版建议先用 `CSI amplitude`。

原因：

- 幅度特征更容易上手
- 相位更依赖校准和清洗
- 原型阶段的核心是先验证场景区分度

### 8.2 推荐特征

- 子载波幅度均值
- 子载波幅度方差
- 子载波幅度极差
- `|ΔCSI|` 的均值、峰值、能量
- 短时方差
- 事件突发持续时间
- 多子载波 `PCA` 主成分能量
- `STFT` 或频谱图能量分布
- 事件后静止比例

## 9. 模型建议

### 9.1 推荐开发顺序

不要一开始就上大模型，建议按下面顺序推进：

1. `阈值 + 状态机`
2. `RandomForest / XGBoost`
3. 小型 `1D CNN`
4. 小型 `CNN + GRU`
5. 量化后评估是否部署到 `ESP32-S3`

### 9.2 为什么先做传统模型

- 更容易解释误报来源
- 对小数据集更友好
- 训练和调试速度更快
- 便于快速判断这个场景是否值得继续投入

## 10. 训练数据采集方案

数据集质量决定最终效果。

### 10.1 推荐类别

- `fall_forward`
- `fall_backward`
- `fall_side`
- `sit_down_fast`
- `sit_down_normal`
- `lie_down_on_bed`
- `bend_pickup`
- `walk_pass`
- `stand_still`
- `empty_room`

### 10.2 采集建议

- 每个人每类先采 `30` 到 `50` 次
- 先找 `3` 到 `5` 个人
- 尽量覆盖不同身高和体型
- 每条样本保留事件前后完整上下文
- 记录环境元数据：
  - 房间编号
  - 设备坐标
  - 天线方向
  - 路由器信道
  - 时间段

### 10.3 数据切分注意事项

训练和验证不要只做随机窗口切分，建议至少做两种验证：

- 按“人”切分
- 按“场景”切分

否则很容易出现数据泄漏，离线准确率看起来很高，实际部署效果却很差。

## 11. 推理逻辑建议

最终判断不应只依赖单次窗口分类，建议使用事件级状态机：

1. 运动门控触发
2. 在 `1.5s` 窗内做跌倒候选分类
3. 若分数超过阈值，进入 `suspect_fall`
4. 继续观察 `5s` 到 `10s`
5. 若后续持续低活动，则判定 `confirmed_fall`
6. 触发本地告警并上报

这种两阶段逻辑通常明显优于单次窗口直接判定。

## 12. ESP32-S3 端任务划分

建议在 `S3-RX` 上至少拆分如下任务：

- `wifi_task`
  - 初始化 `Wi-Fi`
  - 启用 `CSI`
  - 注册回调

- `csi_worker_task`
  - 从队列取出 `CSI`
  - 做轻量清洗
  - 写入环形缓冲区

- `motion_gate_task`
  - 接收 `esp-radar` 或 `esp_wifi_sensing` 的活动状态

- `event_task`
  - 管理候选事件窗口
  - 维护状态机
  - 决定是否触发告警

- `uplink_task`
  - 通过 `UART / UDP / MQTT` 上报数据和结果

### 12.1 不要在 CSI 回调里做的事情

- `FFT`
- 文件写入
- 网络发送
- 大量日志输出
- 模型推理
- JSON 大对象拼接

回调路径只做轻量搬运，否则丢包和时序抖动会很明显。

## 13. 初期参数建议

为了降低变量数量，建议在 `V1` 阶段锁定以下条件：

- 只用 `2.4GHz`
- 固定信道
- 固定带宽，优先 `HT20`
- 固定发包路径
- 固定节点位置
- 单房间
- 单人

原型阶段最怕的不是精度偏低，而是实验条件不断变化，导致无法定位问题来源。

## 14. 项目里程碑

### 里程碑 1：打通 CSI 采集

目标：

- `ESP32-S3` 能稳定接收 `CSI`
- `PC` 能实时看到原始幅度变化

### 里程碑 2：实现人体活动检测

目标：

- 能稳定区分 `空闲 / 有人活动`
- 确认链路和部署位置有效

### 里程碑 3：建立数据集

目标：

- 完成跌倒和非跌倒多类别采集
- 建立基础标注规范

### 里程碑 4：离线训练基线模型

目标：

- 在 `PC` 上训练 `XGBoost` 或 `RandomForest`
- 用混淆矩阵评估误报与漏报

### 里程碑 5：集成原型告警

目标：

- 板端完成门控和事件管理
- `PC` 或网关完成最终推理
- 可输出蜂鸣器或消息告警

## 15. 成功标准

建议把 `V1` 成功标准定义为：

- 单房间、单人、固定部署下可运行
- 对明显跌倒事件有较高检出率
- 对 `坐下 / 躺下 / 弯腰` 的误报处于可接受范围
- 多次重复测试结果一致

不要把第一版目标定为“医学级可靠性”或“通用全屋多人检测”。

## 16. 不建议一开始做的事

- 多人场景
- 全屋漫游检测
- 单板蹭家用路由器就追求高可靠
- 一开始就把深度模型塞到板端
- 只看 `accuracy`，不看误报和漏报

## 17. 建议的 V1 实施方案

如果要快速落地，我建议这样定：

- 硬件：
  - `2 x ESP32-S3`
  - `1 x 路由器`
  - `2 x 外置天线`
- 软件：
  - `ESP-IDF 5.5.x`
  - `esp-csi`
  - `esp-radar`
  - `esp_wifi_sensing`
- 板端职责：
  - `CSI` 采集
  - 运动门控
  - 候选事件切窗
- `PC` 端职责：
  - 数据记录
  - 特征提取
  - `XGBoost` 训练与在线推理
- 最终判定逻辑：
  - `剧烈变化 + 分类器 + 事后静止确认`

## 19. 下一步建议

可以沿两个方向继续推进：

### 方向 A：工程实现

先写一个最小 `ESP-IDF` 工程，完成：

- `CSI` 采集
- 串口/UDP 数据上报
- 活动门控
- 事件切窗

### 方向 B：算法验证

先定义数据格式和采集协议，完成：

- 原始数据记录格式
- 标注文件格式
- `Python` 基线训练脚本
- 简单可视化工具

如果项目目标是尽快出可演示结果，优先做 `方向 A`。如果项目目标是验证跌倒识别精度，优先做 `方向 B`。
